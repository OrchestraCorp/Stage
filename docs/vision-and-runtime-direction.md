# OrchestraCorp 愿景与 Stage 自研运行时方向

## 1. 已确认的产品方向

OrchestraCorp 的终极愿景是：**AI 驱动的、安全可靠的、分布式工作协作平台。**平台面向跨地点、跨时区、跨组织的人与 Agent，支持成员在流动生活和远程工作中保持明确身份、责任、协作关系与可验证结果。

2026-10-24 用户明确了两项架构取向：

1. Stage 从初期自研与 Cordis 组件思想深度配合的运行时和工作规范。Graphon / Dify 仅作为研究参考，不作为 Stage 产品依赖，也不建立先接入再替换的实施路线。
2. 分布式组织采用可验证身份、明确授权、可审计治理和跨组织协作；不将区块链、代币或链上共识作为平台前提。

随后用户明确一期先打好类 Cordis、身份验证和WASM整体基座。本轮按这一优先级重排[一期方案](phase-1.md)，并将完整任务业务后置保留。

以上是已确认方向。本文其余模块划分、契约和实施顺序是据此提出的设计方案，仍需规格评审和实现验收。本文不批准任何真实组织政策，不表示运行能力已落地。

## 2. 愿景怎样约束产品

| 产品目标 | 建议的工程约束 |
|---|---|
| AI 驱动 | Agent 可以理解、提案和在有效委托内执行；所有动作有身份、范围、预算、责任主体与回执，能够暂停和接管 |
| 安全可靠 | 批准、激活、执行、提交、外部确认分别记录；状态未知时可对账，不以模型输出替代业务事实 |
| 分布式协作 | 跨时区异步交接，任务与承诺长期保存；重连后能核对结果，重复请求不会重复产生业务事实 |
| 可验证组织 | 明确谁依据什么任职或委托批准、执行、验收；对跨组织凭证定义信任来源与撤销规则 |
| 隐私保护 | 个人工作上下文与企业共享事实分开；只共享完成协作所需的数据与证明，查询、附件、日志、通知均有读者范围 |

分布式工作方式、治理权分布和服务多节点部署分阶段建设。初期可以由单个 Stage 部署支持分布各地的成员；跨组织协作也不等于允许请求跨租户自由访问数据。离线创建的草稿与命令在重新连接后，仍须基于当前权限和对象版本核验。

## 3. 各产品承担的责任

| 产品 | 在愿景中的责任 |
|---|---|
| ScoreBook | 保存规则、岗位契约、知识、提案与批准版本，为运行提供可追溯依据 |
| Maestro | 帮助组织理解目标、设计蓝图、协调人员与 Agent，通过受权接口提出或执行动作 |
| Virtuoso | 个人的工作与 Agent 入口，支持可控交接、隐私边界和任务协作 |
| Stage | 构造可信身份上下文、核验授权与批准、执行组织协作规则，保存当前事实和实际运行结果 |

四者保持明确的产品与仓库边界。Maestro / Virtuoso 的模型能力仍由各产品承担；Stage 保存受权业务需要的身份、委托、运行和回执，不扩展为 MaaS 平台。上述边界延续 [AGENT.md](../AGENT.md)。

## 4. 深度配合的自研运行体系

Stage 采用统一契约、分工明确的运行体系：组件内核与业务流程运行器都由 Stage 实现，共享能力目录、版本解析、可信执行上下文、故障语义与追踪身份。

| 部分 | 责任 | 状态归属 |
|---|---|---|
| Component Runtime | 服务依赖、provider、资源 owner、generation、就绪与排空清理 | 进程与组件生命周期 |
| Workflow Runtime | 节点、分支、汇合、循环、人工等待、定时、恢复与实例迁移 | 持久流程实例 |
| Capability Catalog | 定义版本化能力、配置与输入输出契约、所需权限和执行预算 | 不可变定义与受控注册 |
| Command Kernel | 当前授权、对象版本、幂等、领域不变量、事务、审计和 outbox | 持久业务事实 |
| Blueprint / Release | 编译确定的执行计划、变更预览、批准、签名、激活及撤销 | 发布与治理记录 |
| Identity / Authorization | 主体、成员、任职、关系、委托、认证证据与当前判定 | 权威身份与授权事实 |

一次流程步骤的建议路径为：

```text
解析该实例固定的计划和能力版本
→ 取得本次步骤所需 provider 的代次租约
→ 根据执行身份与委托引用构造可信上下文
→ 经过授权的查询或命令入口
→ 在事务内重验并提交业务结果、审计和 outbox
→ 记录可恢复的步骤结果，释放本次租约
→ 继续调度，或持久保存等待状态
```

对外部系统的动作在事务提交后交给受控投递；未收到确定回执时记录 pending / unknown，并通过幂等键对账。跨数据库或跨组织动作另定消息与补偿协议，不能继承本地事务的原子性声明。

每个逻辑步骤固定 execution 与业务幂等身份；重试可生成新的 attempt，但不能更换同一业务动作的幂等键。同库部署时，业务结果与步骤完成 / 恢复唤醒记录应在同一事务提交；跨存储时，通过业务事务中的 outbox 和幂等消费、查询 CommandExecution 对账推进。不能因为流程尚未记下完成，就再次产生已经提交的业务副作用。这是后续持久流程必须验收的崩溃窗口。

“深度配合”具体要求：

- 组件可以注册能力及其版本化 handler；编译器和流程运行器从同一能力定义解析配置、输入输出与执行绑定。
- `ComponentContext` 管资源，`ExecutionContext` 管一次受权动作；组件中不保存长期共享的“当前用户”或“当前公司”。
- 流程实例固定所用定义与实现版本；本次步骤再绑定实际 provider 代次。版本不可用时明确等待、失败或按已批准方案迁移，不静默回退 latest。
- 人工等待时释放步骤级执行资源，不持有数据库事务或 provider 租约。实例保留持久定义引用，确保旧版本不会被错误回收。
- 升级时停止旧代次接入，完成在途步骤、记录结果并排空后再退役；中断状态能够从持久记录判断，不能把卸载 disposer 当成业务回滚。
- 组件 hook、流程调度事件、领域事件、审计和外部投递分别定义；运行框架不能把权限检查当成失败可忽略的观测回调。
- 身份验证、授权强制入口和发布信任根属于受控平台配置；普通业务蓝图不能替换这些规则以扩大自身权限。

这些约束允许业务模块与运行内核共同演进，同时保持持久业务事实独立于某个进程的生死。

## 5. 自研工作规范的边界

规范先服务于 Stage 的实现与验收，再根据实际互操作需求演进。暂不把讨论中的规范名称当成已发布行业标准，也不承诺兼容其他引擎的全部 DSL。

| 契约范围 | 必须明确的内容 |
|---|---|
| 组件与资源 | 依赖、服务键、代次、owner、启停、取消、清理失败；沿用现有 `stage-runtime-core-v1` 草案 |
| 能力与蓝图 | 能力版本、类型、配置默认值、组织选择器、作用域、编译结果、依赖锁和语义差异 |
| 身份与执行 | actor、有效责任主体、任职、委托、租户、认证证据、当前授权与原因码 |
| 流程状态 | run / frame / node / attempt 的身份，分支与汇合，等待、重试、暂停、取消、恢复和迁移 |
| 批准与发布 | 批准对象摘要、能力上限、目标环境、前置版本、签名、激活回执、撤销与信任根变更 |
| 持久副作用 | 事务提交、稳定幂等、外部 attempt、未知结果、对账与补偿 |
| 扩展执行 | WASM 宿主接口、版本、预算、执行隔离和结果语义；底层引擎单独选型 |

每项正式契约需同时提供术语、数据schema、状态转换、错误与恢复、版本兼容规则、正反例和一致性场景。已定义34个Core场景，执行/通过为0；新增身份、WASM、对象与联调场景分别统计，不计作已验收能力。Graphon可帮助发现边界条件，Stage行为由自己的规格决定。

自研范围是组织协作运行语义与控制逻辑。密码学、身份协议、数据库、WASM 引擎等基础设施仍应采用经过核验的实现；不因为自研运行时而自创密码算法或 WASM 虚拟机。

## 6. 分布式治理与隐私的演进原则

一期实现真实协议认证、当前任职/委托授权与受控WASM纯计算，再按跨组织需求引入可验证凭证、最小披露与多方治理。WASM宿主在一期规划中，但不因此宣称已有密码学隐私、身份唯一性或去中心化信任。其输入输出、签名和隔离边界见[WASM规格](wasm-host-design.md)，隐私概念修正见[核对记录](design-review-2026-10-24.md)。

后续隐私方案必须分别回答：谁能签发、谁信任谁、证明绑定哪个操作与挑战、凭证如何撤销、需要披露什么、何处需要可追责或防重复。若采用选择性披露，不应在证明通过后又无条件取回完整个人资料；应按场景确定当前授权所需的最小可信输入。

多方批准策略和实际密码学签名方案分别设计。业务包不能修改自身的信任根或验签要求。隐私证明、阈值签名和跨节点协调均需独立的威胁模型与验收，不从 DAO 愿景直接推导某种协议已经适用。

## 7. 交付顺序

1. **P1：Core＋身份＋WASM基座。**自研Core、真实协议认证、当前授权、受控runner、签名准入通过最小资格评估闭环联调；暂不开放通用流程DSL。
2. **P2：任务切片与蓝图发布。**实现保留的任务/容量/交付/验收，扩展有限蓝图、确定计划、语义diff和组织发布治理，细化自研流程协议。
3. **P3：通用持久流程。**扩展自研调度、分支、循环、人工等待和恢复，验证重复投递、撤销竞争、版本保留及显式迁移。
4. **P4：多节点与跨组织运行。**先明确每类事实的权威与一致性，再验证消息、租约、旧执行者拒绝写入、版本升级及故障恢复。
5. **P5：扩展互操作与隐私能力。**在一期WASM宿主之上评估有限hostcalls、WIT/Component Model、可验证凭证和最小披露；每项独立验收，不自动继承一期纯计算保证。

自研的长期成本主要在并发、恢复、兼容性和安全维护，因此以窄范围规范和可复现验收扩展能力。[核心对象](core-object-contracts.md)现已形成第一版对齐稿，下一步评审schema与基座验收边界；本轮文档不触发代码开发。
