# Stage 长期目标与阶段路线

当前私有化部署以一实例一个组织授权根为边界；根不等同法人公司，组织单元、scope 和跨实例身份分别建模。本文保留的 tenant 字段指兼容的组织根引用，长期多节点不是 SaaS 多租户。详见[组织授权根语义](organization-root-semantics.md)。

## 1. 长期目标

Stage 最终提供一个可审阅、可组合、可恢复的组织协作后端。同一套任务、审批、记录、通知和连接能力可以通过受控配置服务于不同组织；Maestro 提出配置与执行计划，Stage 核验授权、执行确定性规则并保存事实，Virtuoso 使用同一事实完成个人工作。

2026-10-24 确定的上位愿景是 **AI 驱动、安全可靠的分布式工作协作平台**。Stage 自研组件运行时与业务流程运行器，Graphon / Dify 仅作为研究参考。可验证的分布式组织不以区块链为前提，跨地点协作、跨组织治理和多节点部署分别推进，见[愿景与自研方向](vision-and-runtime-direction.md)。

本轮进一步明确一期基座优先：Core、真实人员身份认证、受控 WASM 与最小签名准入先联调，完整任务业务随后扩展。早期协作采用**人员—公司—人员**模式，Agent 仅是人员监督使用的工具，不独立入职、任职、承诺或验收，不拆 Agent 专用业务接口。对应对象与阶段以[人员协作边界](people-company-collaboration.md)、[核心对象](core-object-contracts.md)、[一期方案](phase-1.md)为准。保持可信人员身份、明确任职、对象版本、读者范围、持久事务与可追踪外部结果。

独立 Agent 主体、AgentRegistration、AgentWorkloadBinding 和 Delegation 仅作为长期候选，没有默认实施时间表，不随 P1b、P2 或 P3 自动启用。ServiceGrant 只在真实技术后台任务有独立授权需求时另案，不作为 AI 辅助协作的前置条件。已有 service 认证属于技术来源事实，不授予组织成员业务权。

运行时与能力组合的统一决策入口是[运行时演进与能力组合决策](runtime-evolution-and-composition.md)，其中明确 Component Runtime、Execution Kernel、Workflow Runtime 的边界，以及 Cordis/Dify 仅作机制研究参考。

## 2. 阶段划分

首个正式管理切片已完成服务端实现与复测：现有人员目录、首管本人接受、有限普通任职授撤、管理审计及原键恢复，见[具体合同](human-administration-first-slice.md)。员工激活、组合离职和多管理员管理权变更仍是后续明确切片；本轮不提前增加完整组织岗位或通用流程。

2026-10-26 用户确认：完整的身份／人员／权限管理界面融入Maestro，Stage提供管理API、当前管理授权、生命周期操作与审计。云端Stage和本地Maestro通过版本化合同协作，见[管理中心边界](maestro-stage-administration.md)。近期以人员／账户／有限任职的最小管理闭环补足P1b；管理中心是各阶段能力的共同产品入口，完整组织岗位仍按P3推进，不把全部目标模块变成P1b退出门槛。每个切片以真实管理员操作及两端联调验收，不把dev/test CLI或只有页面算完成，也不借此提前扩建通用OA流程平台。

2026-10-26 同步确认：Maestro 可保存多套 Stage 连接并显式切换；每个连接绑定独立 issuer、会话、主体、任职、缓存和未知结果恢复。该能力是客户端连接管理，不能转化为 Stage 多租户或跨实例全局身份；具体合同见[多 Stage 连接与切换](maestro-multi-stage-connections.md)。

2026-10-26 已按[代码复查](reviews/code-state-and-next-steps-2026-10-26.md)把近期实施拆为本人任职发现、MFA 的窄配置变更与强度验证、Maestro 实际人员闭环。该记录之后，本人任职查询和 MFA 配置/强度/新鲜度已由 [P1b.4](reviews/p1b4-assignments-mfa-2026-10-26.md)实现并有真实隔离协议证据；阶段目标不因局部交付而提前完成。

P1a 已按证据完成；P1b.1/.2 已有真实身份与内部人类授权，P1b.3 将真实认证证据、当前单任职与已有工作项元数据命令接入同一链路。最小人员路径的 Stage 侧收尾见[复查与并发记录](reviews/p1b-closeout-2026-10-25.md)；P1b.4 已提供本人任职发现和组织统一登录 MFA，用户选定密码＋TOTP；随后[原生认证模块](native-authentication-design.md)实现服务端密码＋TOTP、绑定/恢复与最小 OAuth/OIDC；整体 P1b 仍需 Maestro 桌面登录/任职选择及实际用户恢复交互验收，生产接入单独验证。正式入离职与权限管理按具体最小切片确定，不默认扩建完整 IAM。其余阶段仍为目标，没有承诺日历工期或已完成比例；最小编辑接口不等于完整任务业务或整期完成。

2026-10-26 的[授权与业务并发改进提案](stage-concurrency-improvement-plan.md)是 P1b 已实现底座的有限整理，不新增阶段，也不代替 Maestro 联调或 P1c/P1d。先明确验证职责、短事务锁序和同键恢复，再按真实 PostgreSQL 竞争与容量证据验收；P1c 接口设计可以并行，新的事务实现采用届时已验证的协议。不得把本轮演化成无限期性能平台工程。

路线兼容门槛见[阶段接缝](stage-concurrency-improvement-plan.md#route-compatibility)与[过渡项退出条件](stage-concurrency-improvement-plan.md#transition-exits)：本轮移除旧隐式锁默认兼容入口；UUID 结果恢复在新增生产消费者之前完成局部恢复协议；Outbox 在首个真实 Worker 启用前另验。P1d 已要求持久 attempt 条件终态与旧回执拒绝，P4 的跨节点租约/fencing 是后续加强，不能将所有旧执行权保护都推迟到 P4。锁键编码／协调后端的版本切换按[升级边界](stage-concurrency-improvement-plan.md#coordination-upgrade)处理，当前采用停接入、排空和确切制品切换，不宣称已支持混合版本滚动运行。

P1a 按[框架实施规格](framework-foundation.md)完成资源/依赖内核、安全退出/组合、provider/应用装配。P1b.3 以人员元数据编辑闭合认证到命令；P1b.4 已实现本人任职查询和密码＋TOTP 的组织策略，接下来完成 Maestro 实际客户端与因素绑定/恢复验收，并按实际入口核对剩余证据。登录 MFA 和 P1c/P1d 中绑定具体业务意图的批准分别建设；服务端 MFA 验证不等于桌面或业务批准完成。独立 Agent 身份平台不构成门槛，完整任务领取/交付/验收不随最小编辑接口提前进入 P1，详见[P1b 入口](p1b-implementation-entry.md)。

运行时演进以真实后端故障场景为验收目标，不以 Cordis API 相似度为目标。当前 `ComponentContext` 只管理后端组件激活代次、依赖、资源 owner、进程内任务和调用租约；`ExecutionContext`/`AuthorizationContext` 负责业务身份与授权，PostgreSQL 负责持久事实和结果。后续每增加一层能力，都必须先说明重启是否要保留状态、是否跨越外部副作用、未知结果如何查询、撤销/版本何时重验，以及停止时怎样停接入、排空和释放。

P1 完成身份、受控 WASM、签名准入和 `EvaluateQualification` 纵向闭环后，优先建设一个真实连接器与 Durable Worker：连接器提供 health/invoke/query/close 等受控边界，调用带 deadline 和稳定幂等键；Worker 从 PostgreSQL outbox/attempt 领取持久工作，停止时先停止新领取再排空在途调用，外部超时保留 `unknown`。这一步验证 Runtime 对连接器和 Worker 的实际价值；`ctx.spawn()` 仍只承担进程内监督。

Worker 和 runner 是技术设施。后续人员发起的排队工作保留原人员、成员经历、选定任职与原命令因果链，执行和提交时重新授权；工具辅助不能充当人工确认。持久任务机制不会自动产生一个 Agent 业务参与者或 ServiceGrant。

P2 继续使用统一 Execution Kernel，先交付一条明确的人员业务闭环，再以真实配置/替换需求扩展有限能力目录和蓝图发布；业务模块从现在就可按受信组件组织，不等待通用组合平台完成。不提前建设通用 DSL、插件市场或任意代码热插拔。P3 再建设持久 Workflow Runtime；人工等待释放事务和组件租约，恢复时重新验证当前授权、定义版本和对象版本。P4 只有在容量或故障证据成立后才扩展多进程、多节点、fencing 和滚动升级；P5 只有在有真实消费者和威胁模型时才扩展 WASM hostcall/WIT/隐私能力。

## 3. P2：业务切片与声明式装配

完整任务业务的[六种操作、容量与独立验收](business-slice-plan.md)在P1基座后实现；其数据与授权依赖一期共同契约。P1签名准入只覆盖固定模块清单，P2扩展为完整蓝图和组织发布治理。

蓝图描述模块 ID / 版本、依赖键、非敏感配置、realm、接口版本与启用条件。凭据由部署秘密引用取得，不放入蓝图、浏览器包或普通审计。首版蓝图使用 schema 验证的数据，不解释任意 `!!js`、`eval` 或 Agent 生成的 Python。

配置应用协议为：

```text
生成候选 revision
→ schema / 版本 / 依赖 / 环 / 权限 / 资源预检
→ 固定计划、依赖与能力范围，生成受影响组件和在途工作计划
→ 按当前组织规则批准精确摘要，签署面向租户与环境的发布许可
→ 核验批准、签名、撤销状态及 expected_active_revision
→ 串行激活；涉及 provider 换代时执行停接入、drain 与重配
→ 记录 observed revision、各组件结果和恢复状态
```

desired revision、已批准 revision 和实际 observed revision 是不同对象。不能因为 Git 合并成功就报告 Stage 已激活，也不能因为目标配置合法就把半数成功的应用报告为整体成功。

发布许可覆盖蓝图 / 计划摘要、依赖版本、能力上限、目标租户与环境、前置 revision 和发布序号；具体签名及审批协议需单独评审。蓝图不能修改自己的信任根。每次业务执行仍检查当前主体与资源权限。只修改租户业务规则时，不应无条件重启整个平台的 provider。

P2 不默认承诺事务化 Loader。多个 provider 的启动可能包含不可逆外部准备，恢复需要记录具体完成步骤。preflight 失败保留旧组合；应用中途失败则保持必要入口关闭，报告受影响组件并执行明确恢复计划。所谓“恢复旧配置”必须重新验证资源、版本和外部状态，不能仅还原配置文件。

兼容性由服务键和接口版本、配置 schema、测试场景共同表达；Python Protocol 或类型检查通过不证明两个实现具有相同事务、权限或错误语义。

## 5. P4：分布式协调与更新

多 worker 各自拥有 ComponentContext 和服务图。PostgreSQL 17 保存部署组合的 desired revision、实例 observed revision、激活结果及权威业务租约。Redis 8 可提供非权威短期协调和可丢失唤醒，但进程须回查 PostgreSQL 并能从消息遗漏恢复。持久消息带业务版本和执行上下文引用，处理器执行前重新核验当前权威事实。

进程间的 provider 使用版本化异步协议：截止时间、幂等、错误类别、取消请求、关联 ID 和回执查询必须显式。远端不可达意味着依赖不可用或结果未知，不代表请求未执行。

需要跨节点单一执行者的工作使用 PostgreSQL 持久租约和 fencing token，存储或外部适配器拒绝过期执行者写入。Redis 的 key/锁/TTL 不作为该权威记录。租约到期只是控制权变化，不能自行证明旧进程已停止或旧外部操作未发生。

跨组织协作前先定义各方权威事实、信任来源、授权委托、数据最小披露与结果争议处理，再选择消息及一致性协议。允许地理分布的成员协作，不代表已实现多方共识、完全离线执行或跨组织原子事务。

滚动升级优先采用版本化 worker / 进程：新实例通过 readiness 后接新流量，旧实例停止接入并排空。数据库迁移采用与旧新版本共存兼容的前向变更；二进制回退不等于数据库和外部副作用回退。

无停机、性能提升、热替换开销和企业内并发规模都需要与固定组合基线做可复现测量，当前不提供未经测量的吞吐或可用性承诺。故障注入至少覆盖某 worker 停在旧 revision、broker 路由旧实例、outbox 重复投递和 drain 永不完成。

## 6. P5：代码替换与不可信扩展

配置重组、替换 provider 实例和替换 Python 模块代码分开管理。`importlib.reload()` 会留下旧对象引用问题，不能替代运行时的代次、排空、状态迁移与发布协议。[S4]

生产优先验证进程替换；只有当进程重启成本、状态需求和真实场景证明有收益时，再实现限定模块类别的进程内 HMR。需明确哪些状态保留、迁移函数及版本、清理失败后的终止方式、回退可行性。C 扩展、全局 monkey patch、未受管线程等可直接列为不支持热替换。

P1已经规划标准Core WASM纯计算、独立runner与签名准入；P5在此基础上扩展宿主接口、SDK和跨语言互操作，不能把未来hostcall的权限保证倒算到一期。Context的依赖声明与realm不是安全沙箱。跨语言TS插件可研究Node provider bridge，但不宣称Python能直接运行现有DSH插件。

只有发现多个独立应用消费者，并且 Stage 业务类型不再泄漏到 runtime，才评估拆出独立 Python 框架仓库。第一期不新增共享 Runtime 仓库，也不改变 Maestro / Virtuoso 的独立维护方式。

## 7. 全生命周期不变式

- 已提交业务事实不受组件卸载撤销；改变事实必须执行新的受权命令。
- 业务查询、执行、幂等重放和通知都保持 tenant 与读者范围。
- 旧请求、旧租约和旧 disposer 不能污染或删除新代次资源。
- 所有成功声明带有明确提交或观察依据；无法确认就保留 pending / unknown。
- 事件 hook、领域事件、审计、outbox 各自承担明确职责，不合并成一个万能 event bus。
- 所有已声明兼容范围都能定位到参考版本、测试场景、通过记录与有意偏差。

## 8. 待决事项与决策门槛

| 事项 | 当前设计默认 | 最晚何时确认 |
|---|---|---|
| 原生认证与生产部署 | 最小本地 issuer＋成熟库；Keycloak 为历史兼容来源 | 原生 profile 已固定；生产前验 HTTPS/key 管理、恢复责任、容量及 Maestro 实际客户端 |
| 存储部署与容量 | 2026-10-25 已确定唯一主库 PostgreSQL 17＋辅助 Redis 8；MySQL 不再是待选项，见[存储策略](storage-strategy.md) | 生产前固定 PG 备份恢复、Redis 故障策略、容量与访问边界；新增能力须有实际目标环境证据 |
| 生产环境是否自托管与部署规模 | P1单worker宿主＋受控runner子进程，不预设公司规模 | P1c前明确验收OS隔离；真实部署前决定网络、备份和恢复指标 |
| WASM引擎/ABI/预算与签名profile | P1参考Wasmtime、有限Core bytes ABI和固定签名profile；参数仍需冻结 | P1c实现前锁版本、平台、编码、算法与资源限额，并有负向验收 |
| 容量口径与时间模型 | P2业务切片单位计数、单名额；非真实工时 | 扩展多岗位 / 多任务并行前 |
| 动态装配权限与审批人 | 受控运维入口；Maestro 只提案 | P2 的 apply API 开放前 |
| 自研流程规范与范围 | 明确由 Stage 自研，Graphon 仅供研究对照 | P2 定义能力 / 节点 / 实例 / 发布契约；P3 实现前冻结首批状态语义与恢复验收 |
| 多进程协调与 broker | 无一期默认实现 | P4 前，基于吞吐、隔离和故障恢复需求决定 |
| 审计 / 附件保留、删除及读者策略 | 不自行虚构法定期限或企业政策 | 真实数据进入前由明确责任岗位审阅 |
| Python runtime 是否独立开源 | 当前留在 Stage，明确模块边界 | 出现第二个独立消费者和维护资源后 |

生产品牌与长期规模尚未确定，不阻止按虚构数据设计P1；但测试IdP/profile、ABI、签名编码与运行平台必须在相应实现前固定。每次决定更新规格与验收证据，不能只留在聊天里或默认成无限兼容。资料依据见[本轮核对](design-review-2026-10-24.md)与[原始调研](research.md)。
