# Stage 长期目标与阶段路线

## 1. 长期目标

Stage 最终提供一个可审阅、可组合、可恢复的组织协作后端。同一套任务、审批、记录、通知和连接能力可以通过受控配置服务于不同组织；Maestro 提出配置与执行计划，Stage 核验授权、执行确定性规则并保存事实，Virtuoso 使用同一事实完成个人工作。

2026-10-24 确定的上位愿景是 **AI 驱动、安全可靠的分布式工作协作平台**。Stage 自研组件运行时与业务流程运行器，Graphon / Dify 仅作为研究参考。可验证的分布式组织不以区块链为前提，跨地点协作、跨组织治理和多节点部署分别推进，见[愿景与自研方向](vision-and-runtime-direction.md)。

本轮进一步明确一期基座优先：Core、真实身份认证、受控WASM与最小签名准入先联调，完整任务业务随后扩展。对应对象与阶段以[核心对象](core-object-contracts.md)、[一期方案](phase-1.md)为准。长期保持可信身份、明确任职、有限委托、对象版本、读者范围、持久事务与可追踪外部结果。

## 2. 阶段划分

P1a 已按证据完成，其余阶段仍为设计目标；没有承诺日历工期或已完成比例。不能以目录存在、API 壳子或演示截图代替验收。

| 阶段 | 主要交付 | 进入前提 | 完成证据 |
|---|---|---|---|
| **P1：Core＋身份＋WASM基座** | 自研Core、共同对象、真实协议adapter与当前授权、独立WASM runner、有限ABI、签名准入；EvaluateQualification＋幂等/审计/outbox | 当前底板；Core/IAM/ABI/准入及事务契约共同评审 | Core C1–C8 34项＋S1 12项、所选profile适用I1、W1-01～28、O1-01～07、F1-01～12；O1-08留P3。真实IdP/真库/runner故障留证，不冒充生产就绪 |
| **P2：业务切片与蓝图发布** | 任务/承诺/容量/交付/独立验收；蓝图schema、确定计划与依赖锁、语义diff、扩展批准签名与激活；细化自研流程契约 | P1身份、运行、制品和事务基础通过 | [业务切片](business-slice-plan.md)九类验收；无效配置不破坏当前组合；部分激活失败准确报告；重复应用可对账 |
| **P3：持久流程与组织协作** | 自研 Workflow Runtime 的分支、循环、人工等待和恢复；组织岗位、正式审批、表单 / 记录、SLA、替补接管；ScoreBook 与 GitLab / 身份目录连接 | P2 版本与策略来源明确；自研流程契约及领域授权协议通过 | 旧实例与版本保留、撤销竞争、重复恢复、重试副作用、审批版本、跨系统漂移 / unknown 均有故障注入与真实接口验收 |
| **P4：多进程、多节点与受控升级** | 独立 worker、持久协调、服务 broker、版本化部署、配置代次一致性、滚动切换与恢复 | P1～P3 不变量可在持久层表达；事件与命令版本策略确定 | 节点失联 / 重启、旧任务回写、重复投递、混合版本、故障切换和备份恢复经过压力与混沌测试 |
| **P5：扩展互操作与隐私能力** | 基于P1受控WASM扩展SDK、有限hostcalls与可能的WIT/Component Model；评估隐私凭证、自研runtime独立发布与有条件HMR | 明确消费者、维护资源与威胁模型；各接口与密码协议独立选型 | 扩展行为、宿主能力限制、版本兼容、凭证/最小披露按选定协议实测；不从纯计算WASM推断已支持 |

P3 的单个能力可以在其依赖满足后与 P2 局部并行；P4 不能绕过 P1 的事务和退出协议。拆微服务由隔离、容量与运维证据驱动，不按能力列表机械拆进程。

P1a 按[框架实施规格](framework-foundation.md)完成资源/依赖内核、安全退出/组合、真实 provider/应用装配；原 C、补充 S 和 D-01～D-09 的证据见[P1a 验证](reviews/p1a-validation-2026-10-25.md)。接下来推进真实身份和 WASM。

## 3. P2：业务切片与声明式装配

完整任务业务的[六种操作、容量与独立验收](business-slice-plan.md)在P1基座后实现；其数据与授权依赖一期共同契约。P1签名准入只覆盖固定模块清单，P2扩展为完整蓝图和组织发布治理。

蓝图描述模块 ID / 版本、依赖键、非敏感配置、realm、接口版本与启用条件。凭据由部署秘密引用取得，不放入蓝图、浏览器包或普通审计。首版蓝图使用 schema 验证的数据，不解释任意 `!!js`、`eval` 或 Agent 生成的 Python。

配置应用协议为：

```text
生成候选 revision
→ schema / 版本 / 依赖 / 环 / 权限 / 资源预检
→ 固定计划、依赖与能力范围，生成受影响组件和在途工作计划
→ 按当前组织规则批准精确摘要，签署面向租户与环境的发布许可
→ 核验批准、签名、撤销状态及 expected_active_revision
→ 串行激活；涉及 provider 换代时执行停接入、drain 与重配
→ 记录 observed revision、各组件结果和恢复状态
```

desired revision、已批准 revision 和实际 observed revision 是不同对象。不能因为 Git 合并成功就报告 Stage 已激活，也不能因为目标配置合法就把半数成功的应用报告为整体成功。

发布许可覆盖蓝图 / 计划摘要、依赖版本、能力上限、目标租户与环境、前置 revision 和发布序号；具体签名及审批协议需单独评审。蓝图不能修改自己的信任根。每次业务执行仍检查当前主体与资源权限。只修改租户业务规则时，不应无条件重启整个平台的 provider。

P2 不默认承诺事务化 Loader。多个 provider 的启动可能包含不可逆外部准备，恢复需要记录具体完成步骤。preflight 失败保留旧组合；应用中途失败则保持必要入口关闭，报告受影响组件并执行明确恢复计划。所谓“恢复旧配置”必须重新验证资源、版本和外部状态，不能仅还原配置文件。

兼容性由服务键和接口版本、配置 schema、测试场景共同表达；Python Protocol 或类型检查通过不证明两个实现具有相同事务、权限或错误语义。

## 4. P3：扩展业务能力而保留统一事实

| 能力 | 长期目标 | 延续的关键限制 |
|---|---|---|
| 组织与岗位 | 多岗位任职、替补、资格与工作窗口，维护 / 值班等工作纳入容量 | 容量按实际责任主体累计，不按角色重复计算同一份时间 |
| 审批与签署 | 具体对象版本、参数和有效期的批准证据，职责分离与补偿控制 | 批准不是执行成功；参数改变需重新核验；例外必须可解释和留痕 |
| 工作流 | Stage 自研节点、分支 / 汇合、循环、并行、人工等待、定时与恢复 | 实例固定定义与依赖；每步重验当前权限，等待释放步骤租约；迁移另行批准 |
| 上下文与投影 | 员工 / 管理视图、最小交接上下文、附件、搜索与知识候选 | 索引、缓存、摘要与嵌入继承来源权限，私人会话不自动汇总 |
| ScoreBook | 精确版本引用、结构化规则包、提案 / 审阅 / 加载回执 | 文本制度不直接解释成任意授权代码；运行激活独立于合并 |
| GitLab / 专业系统 | 最小权限身份、MR 回写、实际 ACL 核验与漂移对账 | 专业系统保持自身事实权威；请求成功与外部结果已确认分别记录 |
| Agent 运行 | 绑定委托与任务版本、暂停 / 取消 / 接管、动作回执 | Stage 不托管模型路由；Agent 运行结束不等于业务验收 |

P2业务切片暂定单名额、单位容量仅用于验证原子承诺机制。长期容量单位、时间窗口、并行工时和跨组织兼职口径另定，不能把演示计数直接当成人力核算模型。

## 5. P4：分布式协调与更新

多 worker 各自拥有 ComponentContext 和服务图。PostgreSQL 17 保存部署组合的 desired revision、实例 observed revision、激活结果及权威业务租约。Redis 8 可提供非权威短期协调和可丢失唤醒，但进程须回查 PostgreSQL 并能从消息遗漏恢复。持久消息带业务版本和执行上下文引用，处理器执行前重新核验当前权威事实。

进程间的 provider 使用版本化异步协议：截止时间、幂等、错误类别、取消请求、关联 ID 和回执查询必须显式。远端不可达意味着依赖不可用或结果未知，不代表请求未执行。

需要跨节点单一执行者的工作使用 PostgreSQL 持久租约和 fencing token，存储或外部适配器拒绝过期执行者写入。Redis 的 key/锁/TTL 不作为该权威记录。租约到期只是控制权变化，不能自行证明旧进程已停止或旧外部操作未发生。

跨组织协作前先定义各方权威事实、信任来源、授权委托、数据最小披露与结果争议处理，再选择消息及一致性协议。允许地理分布的成员协作，不代表已实现多方共识、完全离线执行或跨组织原子事务。

滚动升级优先采用版本化 worker / 进程：新实例通过 readiness 后接新流量，旧实例停止接入并排空。数据库迁移采用与旧新版本共存兼容的前向变更；二进制回退不等于数据库和外部副作用回退。

无停机、性能提升、热替换开销和多租户规模都需要与固定组合基线做可复现测量，当前不提供未经测量的吞吐或可用性承诺。故障注入至少覆盖某 worker 停在旧 revision、broker 路由旧实例、outbox 重复投递和 drain 永不完成。

## 6. P5：代码替换与不可信扩展

配置重组、替换 provider 实例和替换 Python 模块代码分开管理。`importlib.reload()` 会留下旧对象引用问题，不能替代运行时的代次、排空、状态迁移与发布协议。[S4]

生产优先验证进程替换；只有当进程重启成本、状态需求和真实场景证明有收益时，再实现限定模块类别的进程内 HMR。需明确哪些状态保留、迁移函数及版本、清理失败后的终止方式、回退可行性。C 扩展、全局 monkey patch、未受管线程等可直接列为不支持热替换。

P1已经规划标准Core WASM纯计算、独立runner与签名准入；P5在此基础上扩展宿主接口、SDK和跨语言互操作，不能把未来hostcall的权限保证倒算到一期。Context的依赖声明与realm不是安全沙箱。跨语言TS插件可研究Node provider bridge，但不宣称Python能直接运行现有DSH插件。

只有发现多个独立应用消费者，并且 Stage 业务类型不再泄漏到 runtime，才评估拆出独立 Python 框架仓库。第一期不新增共享 Runtime 仓库，也不改变 Maestro / Virtuoso 的独立维护方式。

## 7. 全生命周期不变式

- 已提交业务事实不受组件卸载撤销；改变事实必须执行新的受权命令。
- 业务查询、执行、幂等重放和通知都保持 tenant 与读者范围。
- 旧请求、旧租约和旧 disposer 不能污染或删除新代次资源。
- 所有成功声明带有明确提交或观察依据；无法确认就保留 pending / unknown。
- 事件 hook、领域事件、审计、outbox 各自承担明确职责，不合并成一个万能 event bus。
- 所有已声明兼容范围都能定位到参考版本、测试场景、通过记录与有意偏差。

## 8. 待决事项与决策门槛

| 事项 | 当前设计默认 | 最晚何时确认 |
|---|---|---|
| 真实认证profile与生产身份提供方 | P1至少一个真实协议adapter＋隔离测试IdP；fixture仅辅助 | P1b前固定测试profile；真实部署前验issuer/audience/撤销/恢复与主体映射 |
| 存储部署与容量 | 2026-10-25 已确定唯一主库 PostgreSQL 17＋辅助 Redis 8；MySQL 不再是待选项，见[存储策略](storage-strategy.md) | 生产前固定 PG 备份恢复、Redis 故障策略、容量与访问边界；新增能力须有实际目标环境证据 |
| 生产环境是否自托管与部署规模 | P1单worker宿主＋受控runner子进程，不预设公司规模 | P1c前明确验收OS隔离；真实部署前决定网络、备份和恢复指标 |
| WASM引擎/ABI/预算与签名profile | P1参考Wasmtime、有限Core bytes ABI和固定签名profile；参数仍需冻结 | P1c实现前锁版本、平台、编码、算法与资源限额，并有负向验收 |
| 容量口径与时间模型 | P2业务切片单位计数、单名额；非真实工时 | 扩展多岗位 / 多任务并行前 |
| 动态装配权限与审批人 | 受控运维入口；Maestro 只提案 | P2 的 apply API 开放前 |
| 自研流程规范与范围 | 明确由 Stage 自研，Graphon 仅供研究对照 | P2 定义能力 / 节点 / 实例 / 发布契约；P3 实现前冻结首批状态语义与恢复验收 |
| 多进程协调与 broker | 无一期默认实现 | P4 前，基于吞吐、隔离和故障恢复需求决定 |
| 审计 / 附件保留、删除及读者策略 | 不自行虚构法定期限或企业政策 | 真实数据进入前由明确责任岗位审阅 |
| Python runtime 是否独立开源 | 当前留在 Stage，明确模块边界 | 出现第二个独立消费者和维护资源后 |

生产品牌与长期规模尚未确定，不阻止按虚构数据设计P1；但测试IdP/profile、ABI、签名编码与运行平台必须在相应实现前固定。每次决定更新规格与验收证据，不能只留在聊天里或默认成无限兼容。资料依据见[本轮核对](design-review-2026-10-24.md)与[原始调研](research.md)。
