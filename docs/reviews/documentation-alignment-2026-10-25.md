# Stage 定位、插件边界与开发路线文档复查

本轮按用户要求复查开发文档与当前源码，结论是产品方向和分层可继续使用，但文档存在目标提前计入实现、旧提案残留现行权威、登录 MFA 与业务批准混淆，以及派生验收数字漂移。修订只涉及文档与架构图，不改变应用、权限事实、schema 或运行服务，不将文档检查记作功能验收。

## 1. 主要问题与修正

| 问题 | 对开发的影响 | 修正及依据 |

| 历史提案仍像现行规范 | 可能重新引入万能 RuntimeContext、独立 Agent、多租户或预建大部分 OA 的范围 | 9 份早期提案/研究标记历史与替代入口；保留原始观察和数字，不用过去的状态覆盖今天的定位 |
| 旧授权公式用角色/关系/委托的并集 | 容易把资源关系误当成缺失 action 的替代来源 | 历史授权稿增加醒目说明；当前路径必须满足明确单任职 action、对象关系和 ABAC，组织成员身份不自动开权 |
| CapabilityBinding/命令 owned registration 被写成 P1a 已实现 | 下一轮可能依赖不存在的注册 API 或假定有 handler 退役保证 | 对照 [kernel.py](../../app/execution/kernel.py) 与 [work provider](../../app/providers/work.py)：当前固定传入 CommandSpec 集合，外围组件 lease 保活；独立能力注册是 P2 目标 |

Dify 对照另补历史状态和来源复核。P2 业务草案也明确当前固定命令集合可先承载业务，动态登记不是前置；未来创建合同不能向当前已有对象 CommandEnvelope 直接传版本 0，新增角色 action 也不能依靠旧 RoleCode 映射隐式授予。

## 2. 修订后的定位与交付顺序

Stage 是企业私有化部署中的组织协作后端：一实例一个组织授权根，人员承担成员、任职和业务责任；Agent 是受监督工具。Cordis 提供依赖、资源归属、作用域和生命周期的机制参考，Stage 自行负责人员授权、事务、幂等、持久结果与外部对账。功能模块可受控组合，插件数量不构成目标，也不以兼容 Cordis/Dify 作为交付理由。

1. **P1b 剩余**：真实客户端、登录 MFA profile/强度及恢复语义、本人任职发现与选择，逐项补适用 I1 证据。当前 Stage 最小人员链已验证，不能写成完整身份/权限/2FA 产品完成。
2. **P1c/P1d**：受控 WASM、最小制品准入、具体意图批准与组织签名、资格评估闭环；普通登录 MFA 不依赖这部分建成。批准方案冻结后，按实际 profile 验收，不预选 RP 或因素。
3. **P2**：一条实际人员任务闭环；随后按真实模块替换/配置场景建设有限声明式组合与发布。受信业务代码从现在即可组件化，不先造通用蓝图或插件市场。
4. **P3 及以后**：持久流程、多节点、受控扩展各自依据需求与证据进入，不把愿景变成近期全套实现义务。

正式人员/权限管理、账户恢复、生产身份和外部连接器仍有缺口。文档明确这些边界，而不在本轮擅自建设新接口或认定其全部必须纳入当前最小切片。阶段、现状和证据的权威关系统一在 [文档入口](../README.md)。

## 3. 插件开发与停用协议

已补入 [运行时演进决策](../runtime-evolution-and-composition.md#51-新增与停用功能的开发协议)：新增功能先明确领域事实、action、版本和副作用，再按资源/生命周期决定组件边界；当前人员入口应复用已接通的认证/锁协调/提交前重验协议。通用 command_plugin 尚未接人员 identity_validator，不能被当成可直接公开的人员 API 模板。

停用时先关闭新业务接入、停止新任务领取，保留必要的当前授权结果读取/unknown 对账，排空后释放资源。当前没有统一功能移除控制面；required 集合、静态路由、兼容弃用和恢复实现须在实际部署变更中一起处理。卸载不能删除业务记录，历史数据清理单独按迁移/保留政策处理。默认 restart/replace 先排空旧代，再启动新代，不承诺任意插件零停机热替换。
