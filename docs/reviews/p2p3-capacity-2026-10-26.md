# P2 / P3 容量实测与 Runtime 复查（2026-10-26）

状态：开发设备基线已完成，未设定或验收生产 SLO。本文关闭工程审计 P2 E 的测量缺口，并补充 P3 Runtime 所有权复查。组织 guard 的安全锁策略保持。

记录时间：2026-10-26 11:55:27 CST。原始数据：[JSON](p2p3-capacity-2026-10-26.json)；复现脚本：[benchmark_mixed_auth_work.py](../../scripts/benchmark_mixed_auth_work.py)；测量与安全边界测试：[test_mixed_auth_work_benchmark.py](../../tests/test_mixed_auth_work_benchmark.py)。

## 结论

2048 次混合操作和 16 人同时密码＋TOTP 登录全部成功；512 条命令、512 条审计和 512 次工作项版本增加一一匹配。1→16 并发时总吞吐约为 30～33 次/秒，而混合延迟 p95 从 64 ms 上升至 830 ms。增加并发没有带来近似线性的吞吐提升；组织串行锁的获取耗时明显增加。

当前结果支持保留一致性边界，并将锁内重复读取和事务长度作为下一步优化的实测目标。它不支持通过增加连接池或服务进程数量就能提高同一组织吞吐的结论。

## 实验条件

- PostgreSQL 17.11 (Ubuntu 17.11-1.pgdg24.04+2)，通过真实 TCP 连接；独立临时数据库 `stage_test_capacity_20261026`，每次执行先重建该库 public schema 并应用 Alembic，head `c6f3a19d820b`。真实 `stage` 与共享 `stage_test_core` 均未触碰。
- 生产服务方法与 Runtime 调用租约；单进程、单事件循环，连接池 16、overflow 0。16 个合成人员各自拥有独立账号、会话、任职和工作项；一个组织根，强制当前 MFA；RSA 3072 与原生管理工具默认值一致。
- 混合曲线使用 `openid profile offline_access`，四种操作各占 25%；每档 512 次，每类 128 次。每个 worker 串行使用自己的 refresh 链和工作项版本，不制造重复刷新或同对象冲突。
- 先预热各人员的受控读取，再跑 1/4/8/16 闭环并发。混合阶段复用合成的已完成 MFA 状态，真实执行 PKCE 兑换、JWT 验证、刷新轮换和当前业务授权。密码成本由后续独立登录突发覆盖。
- 正式窗口开始前，首轮 PostgreSQL 全量、SQLite 各定向组、Chromium 验收和在线冒烟进程均已结束；最终稳定代码的两套全量在本窗口后重新运行。这是环境描述校正，测量数字、时间和源码指纹未改。常驻 Stage、PostgreSQL、Redis 继续运行；未控制所有宿主机背景活动。
- 可用 CPU affinity 数量 24；1/5/15 分钟 load average 起始为 `[0.19287109375, 0.9150390625, 1.22900390625]`，结束为 `[1.0791015625, 1.01513671875, 1.23681640625]`。没有读取到 cgroup v2 CPU 配额，不能据此声称独占 24 个物理核心。
- 本实验不含 HTTP/TLS、反向代理、WAN、浏览器渲染、Redis 队列或多进程调度；这是服务层 PostgreSQL 基线。

## 测量口径与正确性

`guard_acquire` 从首次 guard SQL 发出前计时，到驱动返回该 SQL 后结束。它包括 PostgreSQL 锁排队、查询执行、驱动及网络往返，属于服务端纯锁等待的上界；不能把它标成精确的 `pg_locks` 等待时间。进入 guard 前的 trust/principal 或连接池等待不包含在这个指标内。

`guard_hold` 从首次成功取得 guard 后开始，直到根事务结束事件。它包括锁内业务 SQL、提交/回滚和连接归还开销，因此略宽于数据库内部实际持锁区间。同一事务重复查询 guard 不重新启动持有计时，也不重复累计持有区间。JSON 同时给出每操作累计值、每事务值、guard SQL 次数及事务数。获取失败的等待不计作成功持有；本次测量没有错误。

SQL 计数通过 SQLAlchemy cursor 事件统计，不包含驱动内部 BEGIN/COMMIT、连接预检等报文。p50/p95 使用线性插值。各类操作吞吐是该类次数除以同一混合窗口总时长，是混合负载中的贡献量，不能解释为该类操作独立运行的容量上限。

确定性测试把第一次 guard 的发出、取得、重入和事务结束时间分别设为 1、6、8/8.5、10：得到获取耗时 5、持有耗时 4，证明持有不包含前面的排队，也没有被重入改成 1.5。另验证清理任务中 ContextVar 已解除时仍归属于原请求。当前测量/fixture 组 SQLite 8 项、独立 PostgreSQL 8 项通过，覆盖真实登录、预算计数与命令审计核对。

## 16 人共享出口登录突发

16 人同时发起一次登录，各自使用独立 TOTP 种子和未消费过的当前动态码。真实执行授权请求限流、Argon2 密码验证、TOTP 消费、浏览器会话建立、授权码和 PKCE 兑换。16 人全部成功，吞吐 9.182 次登录/秒；总延迟 p50 1046.990 ms，p95 1712.497 ms，最大 1737.255 ms。

| 阶段 | p50 ms | p95 ms |
|---|---:|---:|
| authorize | 75.435 | 124.374 |
| password | 893.182 | 1525.543 |
| totp | 18.732 | 27.495 |
| finish | 35.021 | 40.094 |
| token | 22.590 | 24.502 |

每人平均 82 条 SQL、5 个 guard 事务；累计获取耗时 p95 15.925 ms，持有耗时 p95 50.802 ms。主要延迟位于密码阶段，其中包含 Argon2 的有界工作排队，并非大量人员同时持有组织锁计算密码。

没有放宽或关闭限流。按 provider 默认配置，同一传输来源的因素请求预算为 300 次/600 秒，授权请求另有独立 300 次/600 秒预算；实测数据库计数为 32 次因素请求、16 次授权请求，无 blocked_until。密码和 OTP 都各消耗一次因素预算；只考虑正常两步登录时，一个共享出口 10 分钟内的 150 次完整登录就会用完因素预算，后续请求被拒绝，错误密码、恢复等动作还会额外消耗。预算不是“每人 300 次”。本实验只覆盖 16 人低于预算的突发，不能证明大型共享出口登录高峰可承受。

实际 HTTP 来源识别和伪造 X-Forwarded-For 边界由现有 [peer budget 测试](../../tests/native_auth/test_peer_budget.py) 覆盖；本服务层基线不替代生产反向代理配置和 WAN 验收。

## 后续优化约束

1. 先确定预期员工人数、共享出口规模、实际请求混合、峰值到达率与可接受 p95；当前尚无生产 SLO，不能宣称容量已达标。
2. 先优化锁内重复事实读取和短事务长度；若复用当前事务内已锁定事实，必须保留版本/撤销检查、最终期限重验和幂等/审计原子性，禁止未经证明的跨请求权限缓存。
3. 确有吞吐目标后再设计分级 guard：读操作、撤权、凭据变更与业务提交的冲突矩阵及统一锁顺序须先明确，再重跑撤销先行/提交先行的竞争用例和本基线。增加连接池、复制实例或把 guard 直接移到 Redis 都不能自动解决同一组织的串行约束。
4. 独立进行开放到达模型、长时运行、更多真实权限事实、跨进程和代理环境验收；本次闭环 1/4/8/16 曲线、单个登录突发没有覆盖这些问题。

## P3 Runtime 深度复查

- 成功卸载后，host `_records` 移除该 owner，仅保留默认最多 256 条原始值摘要；observations 也默认最多 256 条。旧 scope/context/setup/config 及父组件 children 持有被清除。
- `_ready()` 创建的 PluginHandle 仅为局部临时对象，不进入持久集合；历史摘要不含 setup、config、context、effect scope 或已关闭任务。重复替换不会通过 host 历史累积这些执行对象。
- 失败、blocked、未完成清理仍保留所有权与诊断；成功历史容量不是“整个 host 内存硬上限”。不能用淘汰失败记录来隐藏未释放资源。
- 调用方主动保留旧 PluginHandle 时，原装配 base 仍保留继承配置，以保持后来 `replace()` 的语义。host 摘要不会持有该 base。GC 测试证明旧 handle 保留时 setup 和本组件 config 可回收，最后一个 handle 删除后原 base 配置可回收；不承诺让用户自己持有的引用提前失效。
- `host.close()` 报告本次管理集合，不再重列成功历史；旧 PluginHandle.close() 仍可幂等返回对应 owner 完成。成功句柄的 context 为 None，名称、owner、代次和最终状态保留。

证据：[Runtime 有界历史测试](../../tests/runtime_core/test_history.py)、[Runtime 使用说明](../../app/runtime/README.md)。Runtime Core 76 项、应用 Runtime 70 项通过；固定 Cordis 对照 34/34 参考观察、35/35 共享片段、9/9 预期差异通过。

## 复现与数据管理

需要提前创建独立 PostgreSQL 数据库，并从私密环境注入 TEST_DATABASE_URL。脚本严格只接受 `postgresql+asyncpg` 和 `stage_test_capacity` 或 `stage_test_capacity_<字母数字后缀>`，拒绝真实 stage、共享 stage_test_core 和普通其他测试库；还要求显式 reset 标志。脚本会清空目标库 public schema，不能与其他任务共用该容量库。

```bash
STAGE_ALLOW_TEST_DATABASE_RESET=1 uv run python scripts/benchmark_mixed_auth_work.py \
  --count 512 \
  --output /tmp/stage-mixed-capacity.json \
  --environment-note "记录实际后台负载与是否存在并行测试"
```

输出只包含合成场景、计数、时间与代码指纹，不包含数据库连接串、密码、TOTP 种子、access/refresh token 或签名私钥。实际测量源指纹见 JSON 的 source_sha256，开始和结束相同；它涵盖 app Python、tests/support、新脚本和 uv.lock。基线是该源快照的一次运行，不修改历史验收数字。
