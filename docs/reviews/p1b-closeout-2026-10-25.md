# P1b Stage 侧收尾与身份授权架构复查

本轮按用户要求，在 Maestro 联调之前复查身份权限功能与代码架构，并建立组织 guard 的并发基线。范围是当前人员、单组织根、明确任职、已有 WorkItem 元数据操作；P1b 的客户端验收与 Stage 侧准备分别留证，不能宣称完整 IAM 或全部 I1 场景通过。

## 1. 架构结论

当前分层适合本阶段：IdP 负责登录凭据，IdentityService 验证凭据及当前主体/成员/来源，数据库授权 loader 提供固定任职、角色版本、scope 与 ACL，纯判定引擎组合 RBAC/ReBAC/ABAC，CommandKernel 独占业务事务提交，Component Runtime 管组件和资源生命周期。未发现需要为本切片重建运行时、引入 Agent 身份平台或拆微服务的依据。

| 复查点 | 结论与实际边界 |
|---|---|
| 人员与账号 | 可信 provider/namespace/exact subject 映射；不按 email、用户名或自报 actor 合并身份 |
| 公司与成员 | 一实例一个组织根；成员经历保留历史，重新加入不恢复旧任职；scope 不等于法人/部门主数据 |
| 任职与角色 | 一次选择一个属于当前成员的任职，固定角色 revision；角色代码不隐式开权，不跨岗位并权 |
| 对象授权 | 当前 WorkItem 需要能力＋直接关系＋scope＋可信属性；没有任意关系图、金额或双人规则产品 |
| 撤销与事务 | trust→principal→组织 guard→对象锁；事务外验签，提交前校验身份变化及授权时效 |
| 幂等与读取 | 原人员/命令键隔离；刷新 token 可重放；当前只读任职可恢复本人结果，不能取得新的写权 |
| Core 与业务 | Core 不持人员身份；依赖租约只保活服务。handler 是可信 Python，不是对任意数据库写入的沙箱 |
| 个人管理缺口 | 尚无本人任职列表、资料 CRUD、邀请/入离职和权限管理 HTTP；首轮联调显式交付已登记测试任职，未来选择 UI 需另建只读投影 |

`HumanWorkService` 的对象读取目前直接使用 kernel 的内部授权方法；边界依赖同一受控装配与锁协调，已通过真实路径测试。本轮不为一个读取点增加通用查询框架。增加第二个领域读取入口时，应再评估稳定的事务内授权读取接口，避免复制规则。

## 2. 发现与处理

1. **无效字符串进入数据库查询。** 签名 JWT 的 subject 等 claim 原先允许 NUL，PostgreSQL 文本参数会报存储错误；离线初始化也可能接收该值。现在认证与初始化边界直接拒绝，并补孤立 Unicode surrogate 与合法 Unicode 精确匹配回归。末轮检查同步收紧身份引用、任职/角色及 scope 登记中的控制字符，避免产生接口无法选择或无法查询的授权记录。
2. **HTTP 身份引用与预算说明不一致。** 身份 profile 与工作项任职 query 现统一拒绝空白/控制字符。工作项查询继承公共 IdentityQuery，避免两套 profile 校验漂移；OpenAPI 同步。说明文本除了 20,000 字符，还受既有规范化命令 JSON 的 64 KiB 预算限制，已补合同说明和多字节 Unicode 请求无写入的回归。
3. **恢复边界的测试不足。** 新增跨任职恢复、不同已认证人员隔离、无权限时不泄露版本冲突、最终校验期间任职到期等回归；并行 HTTP 验证不会借用另一人员/任职的权限。
4. **审查记录表达过宽。** 将前轮“handler 修改安全事实都会回滚”收窄为已实测的身份映射误改；任职/角色/ACL 不得由 handler 改写仍属可信代码约束。
5. **外部注销的语义容易误解。** 新增真实 Keycloak 注销验证：refresh 失效后，未到期 access JWT 仍可通过 Stage；随后本地任职撤销阻断读取。该行为是当前离线 JWT profile 的明确边界，内部 evidence TTL 不代表外部账户撤销时限。

未增加业务表、迁移、人员管理写接口或新的权限默认授予。新角色仍由 dev/test 管理员显式登记。没有修改组织锁策略或自动增大连接池。

## 3. 并发基线

执行脚本：[benchmark_human_work.py](../../scripts/benchmark_human_work.py)；机器可读结果：[基线 JSON](p1b-human-work-baseline-2026-10-25.json)。显式允许重置的独立 PostgreSQL 测试库；真实 ASGI→Runtime→身份→授权→命令→PG，使用合成单人员/单组织数据、真实 RSA 签名与模拟 JWKS。单进程/单循环，连接池 5＋5，每档 48 请求。排除真实 IdP 网络、TCP/TLS、Redis 和客户端开销；这不是生产容量或 SLA。

最终基线在全量回归结束后独立运行，脚本在运行前后核对源码摘要；软件版本和摘要见 JSON。基线运行前已完成控制字符输入校验、命令预算说明和授权登记边界的最终代码修订，未改组织 guard、身份/授权事务或基线测量路径；基线运行后只更新文档。因此基线仍用于评估这些业务路径，不能把 JSON 摘要误作当前整棵工作区的提交证明。

文档校正（2026-10-25）：此前派生表与正文沿用了中间批次数字，本次按附带原始 JSON（`recorded_at=2026-10-25T14:37:06.118560+00:00`）同步修正。原始 JSON、源码摘要及测试通过数未改，本轮没有重跑性能测试；上述运行声明仍指原记录批次。

|---|---|---|---|---|
| 1 | 21.36 | 55.49 / 107.12 | 1.61 | 0.02 |
| 4 | 23.62 | 215.11 / 249.31 | 131.36 | 7.64 |
| 8 | 23.38 | 378.05 / 412.74 | 308.74 | 17.01 |

每档 48 次独立对象编辑全部成功且各增加一个版本、一条执行和一条审计；同对象竞争每档只有 1 次成功，其余 47 次明确版本冲突。同键重放不再写入。混合读写期间任职撤销耗时 111.56 ms；撤销完成后开始的 31 个请求全部 403，另做新读/写复查也均 403。

组织 guard 持锁故障下，先由 PostgreSQL 阻塞 PID 证明请求确实在等待：0.5 秒预算请求约 514 ms 返回 503，主动取消路径完成清理；两者均无业务写、无连接泄漏，解除持锁后下一次请求成功。最终 Runtime 完成排空。

连接池指标包含获取/创建耗时，guard 指标包含 SQL 往返和锁等待，均按一次请求的全部获取累计，不能称为纯锁等待或将两个百分位直接相加。

人员认证与业务命令分别取得组织 guard，因此每次编辑存在两段受保护事务。并发增大而吞吐趋于平稳、延迟上升，说明当前串行边界已经可观察；不能靠增加 worker 或连接池直接解除它。尚未给定目标业务负载，本轮保留正确性基线，不据微基准决定共享锁/细粒度锁重构。

后续优化前先固定预期并发、延迟和撤销时限，再评估授权共享读取/撤销独占与对象写锁的组合，统一更改所有 writer，重跑撤销两个顺序、超时、死锁和旧结果保护。IdP/JWKS、WASM、模型或外部连接器请求始终放在业务锁外。
