# 企业 OA 视角的身份、管理登录与权限完备性评估

## 1. 结论

**当前分层方向合理，认证协议与权限执行内核已有较充分的实现和验证；专业 OA 所需的管理员控制面、员工生命周期和安全运营闭环仍未完备。部分能力只是未实现，另一些管理规则尚需冻结，不能概括为“只差前端”。**

核查基线为 `5df49e15f7c9c55b9aebc90cfdb0612a0fc38715`。本次读取当前源码、实际 OpenAPI、现行设计与最近验收，未修改应用／数据库，也未重新执行全量测试或进行独立渗透认证。最近完整验证为 PG1547通过／10跳过、SQLite1454通过／95跳过、真实Chromium两场景，见[并发验收](concurrency-validation-2026-10-26.json)；这些证据证明所覆盖的基础协议，不证明尚不存在的管理员产品流程。

下面的缺口是企业使用闭环的完备性判断，不是已经证实的认证绕过漏洞。生产放行至少需要明确管理员、开户／离职、恢复与审计的最小运营合同；Passkey、目录联邦和全功能 IAM 不自动成为一期前提。

## 2. 已经合理的身份与权限划分

| 层次 | 当前对象与职责 | 评估 |
|---|---|---|
| 登录凭据 | native_account 或明确准入的外部身份；密码/TOTP、credential_version、会话 | 与人员业务权限分开，正确 |
| 安全主体 | Principal；human/service、状态、identity/recovery epoch | 不用邮箱／昵称猜同一个人，不让技术服务冒充人员 |
| 认证来源 | provider/trust、精确profile/version、组织binding、client/audience、MFA规则 | 外部签名有效或OAuth client注册不自动获得Stage业务准入 |
| 组织成员经历 | membership及其生效／终结时间 | 离开后旧经历终结；重新加入不自动复活旧任职，设计合理 |
| 当前任职 | assignment绑定人员、成员经历、scope及固定role revision | 每次操作选择一个任职，避免自动跨岗并权；需要客户端真实选择体验 |
| 能力与数据范围 | 稳定action、角色版本、scope/resource、直接ACL | 能力、范围、关系、状态须共同满足；不是只校验角色名称 |
| 执行与审计 | HumanOperations、CommandKernel、受控管理协议、原生认证专用事务 | 当前授权／期限／版本／幂等及撤销排序由宿主保证，基础较完整 |
| 受监督工具 | Agent／runner属于技术设施，仍以人员责任链发起业务 | 符合一期“人员—公司—人员”，无需独立Agent成员体系 |

主要依据：[权限动作与平台运维角色](../../app/authz/permissions.py)、[当前数据库授权loader](../../app/authz/loader.py)、[身份服务](../../app/identity/service.py)、[组织身份表](../../app/models/identity_foundation.py)、[原生账号表](../../app/models/native_auth.py)。

`platform-operator` 在现有代码中的业务权限集合明确为空。这是正确的防扩权边界，**不代表平台管理员的生产管理能力已经存在**。普通部署操作者有技术控制权，也不应据此在产品层自动获得全部业务资料读取权。

## 3. 完备性矩阵

“已实现”均限定当前受控范围；“有原则”不等于已有可执行状态机和验收。

| 能力 | 设计状态 | 实现／验收状态 | 企业使用仍需补充 |
|---|---|---|---|
| 密码＋TOTP登录 | 已冻结当前协议 | Argon2id、加密种子、OTP防重放、来源与账号预算已实现／测试 | 初始凭据交付、常见/泄露密码阻断策略、实际共享出口标定 |
| 受控多应用OAuth/OIDC | 已冻结选定范围 | PKCE、public/confidential client、SSO/同意、refresh rotation/reuse、退出等已实现 | 生产应用接入验收；第三方本地会话撤销边界 |
| 本人账户安全 | 已有明确协议 | 修改密码、因素重绑、恢复码、本人session/consent管理已实现 | 用户可用的Maestro交互与安全通知；无恢复码时的生产恢复 |
| 组织MFA准入 | 已有版本化规则 | 精确profile/ACR/AMR/auth_time及提交前重验已实现 | 管理员操作的独立强度／新鲜度和降级变更规则 |
| 管理员登录后的管理入口 | 只定义了普通身份及管理操作基础 | 当前管理主要是dev/test OS操作者CLI；无正式管理HTTP闭环 | 管理action、目标范围、可授角色、近期MFA、审计与UI合同 |
| 首次生产初始化与首管交接 | 有bootstrap原则与记录模型 | 开发安装可用；现有管理计划/CLI限制dev/test | 一次性生产安装／首管交接、关闭初始化入口、应急恢复 |
| 入职／开户／激活 | 数据边界较清楚，产品状态机未冻结 | 显式创建开发人员与本地账号、安装任职可用 | 有期限的一次性激活、本人设密／绑定、重复受理和失败恢复 |
| 调岗／离职／复职 | 成员经历与任职撤销原则已有 | 各事实可分开撤销，尚无正式组合管理动作 | 原子撤资格／停登录／撤会话的策略；复职新经历和重新授予；待办移交另案 |
| 正式组织／岗位与个人资料 | 有边界草案 | scope不是组织树；human_profile及正式目录管理未实现 | 人员目录、部门职务与授权scope映射；字段所有者与隐私读者 |
| RBAC/ReBAC/ABAC | 组合设计合理 | 固定角色版本、单任职、scope、直接owner/viewer、当前状态/分类/版本/时间已接入 | 管理域授权、任务派生关系、金额／职责分离等按具体业务补足 |
| 权限管理与解释 | 有内部决策原因与审计基础 | 无管理侧有效权限预览、授予影响预览、完整权限审查入口 | 管理范围／授予上限、自己提权、最后管理员、敏感错误披露规则 |
| 审计与安全运营 | 最小披露和事务留痕原则已有 | 业务audit、control journal、native event存在 | 受权检索／导出、请求关联、保留与清理、通知与处理责任 |
| 生产恢复与密钥生命周期 | 部分运行手册存在 | 私有文件检查、签名ring轮换、开发验证可用 | TOTP主密钥重加密换代、备份回退后失效处理、生产恢复演练 |

## 4. 管理登录的实际缺口

### 4.1 当前有受控管理工具，没有完整的人员管理员控制面

当前实际OpenAPI共25个操作：2个探针、2个本人身份/任职、3个工作项、7个本人账户安全、11个OAuth/OIDC操作。没有员工创建／邀请、人员目录、他人账号重置、成员／任职授予、角色发布、管理员审计检索等端点。

- [管理合同](../../app/control/contracts.py#L8)的Environment限定dev/test。
- [identity CLI](../../scripts/identity_admin.py#L27)用本机hostname摘要＋uid构造operator，并拒绝prod数据库管理入口。
- [native CLI](../../scripts/native_auth_admin.py#L125)的数据库管理也拒绝prod；独立密钥文件生成／候选轮换不等于生产身份管理已开放。
- [管理journal](../../app/control/operations.py#L113)记录bootstrap_operator/local_os_operator；表允许human actor，并不表示已经存在安全的人类管理入口。
- [Permission](../../app/authz/permissions.py#L13)目前没有已接入的员工／任职／账号安全管理action。

因此不能直接给CLI外面套一个HTTP路由，就宣称管理员登录完成。它需要真实人员认证、当前管理任职、目标范围、写者锁协议和人员管理审计；原有可信OS权限不能自动迁移为登录用户权限。

### 4.2 推荐沿用统一认证，明确管理能力

管理员仍是已有Principal，通过同一原生登录／MFA系统认证；Maestro管理页面可以有单独入口、客户端和更短的新鲜度要求，后端依据管理能力决定可做什么。另建一套admin_user/密码库没有当前证据支持。

建议先区分四种责任，而非要求首版必须配四位人员或四套账号：

| 责任 | 典型能力 | 必须限制 |
|---|---|---|
| 部署／恢复操作者 | 安装、密钥和故障恢复 | 独立于普通业务授权；操作可追责，不成为产品内无限业务管理员 |
| 身份安全管理 | 账号停用／恢复、因素恢复、客户端与认证策略管理 | 近期MFA、目标范围、秘密只交付一次、明确恢复证明与通知 |
| 组织权限管理 | 成员生命周期、任职与角色授予 | 可管理哪些人、可授哪些角色版本／scope／有效期、自己的权限边界 |
| 业务负责人／审计读者 | 对具体业务负责，或读取明确范围的审计 | 业务角色不自动成为系统管理员；审计读取不自动允许修改权限 |

**可使用哪些业务权限，与可授予别人哪些权限，需要分开建模。** 例如人事管理者可以按批准规则授予工程岗位，但不意味着其本人自动具有工程业务权限，也不能简单用“只能授予自己已有的全部权限”代替委任规则。首轮应冻结可授角色集合、目标人员／scope上限、期限上限，以及自我授予和角色版本变更的限制。

还需明确：最后一名有效管理员的撤销／到期／因素丢失如何处理；高风险策略降级、管理员权限变化如何审查；何种应急恢复能重新建立管理能力。可以从最小可审计的规则起步，不默认扩建完整PAM或多方审批平台。

## 5. 员工生命周期是当前最需要打通的业务闭环

### 5.1 入职与首次激活

当前原生安装显式绑定已有HUMAN和有效membership，操作者提供初始密码；账号有首次TOTP引导标志，但没有正式邀请／激活到期及临时密码更换状态。[安装逻辑](../../app/native_auth/administration.py)、[账号字段](../../app/models/native_auth.py#L14)

建议正式产品用有期限、单次消费的激活证明，让本人设置密码并绑定因素；定义身份核验、交付渠道、重新发送、失效及结果未知恢复。这里只提出缺口，不预选邮件服务，不把邮箱相同当同人证明。长期让管理员知道员工最终密码不适合作为正式开户流程。

### 5.2 离职不是只撤一个membership

当前业务接口会检查membership，撤成员能阻断相应Stage业务访问。但原生账户认证／UserInfo主要验证principal、account、client和session；[账号锁入口](../../app/native_auth/credentials.py#L67)与[当前会话验证](../../app/native_auth/current_session.py#L39)没有将membership存在作为所有账户安全操作的前提。这是认证与组织权限分离，不能直接归为越权。

需要补的是正式离职动作的目标状态：

- 终结哪一段成员经历、撤销哪些任职与组织权限；历史记录不删除。
- 对普通员工是否同时停用本地账号／principal、撤销SSO和RP会话；保留外部协作者或个人恢复入口时必须显式定义例外。
- 复职新建成员经历并重新授予任职；旧会话、旧任职和旧授权不能随恢复自动复活。
- 待办／审批责任如何冻结或移交属于业务域，历史责任与当前办理权分别处理，不伪称当前最小工作项已具备移交能力。

在同一Stage数据库中的状态变更应按明确写者协议协调，保存执行者、目标、原因、版本与结果。不能串联多个可单独提交的CLI动作，就当成原子离职命令。

第三方应用自行建立的本地会话不在Stage数据库内；当前没有back/front-channel logout通知。接入合同必须说明退出／停用传播方式与时限，不能把Stage侧撤销说成所有网站立即退出。[OAuth边界](../oauth-functional-coverage.md)

## 6. 权限执行较强，权限治理尚未完整

当前单任职与固定角色版本有清晰来源；未知动作、错误scope、失效成员、角色摘要不符、关系撤销、到期及版本冲突都有拒绝路径。这些基础不需要因OA管理需求推倒重做。

当前生产loader支持的关系仍是受控直接ACL；任务assignee/reviewer等未来应由领域事实派生。当前WorkItem loader的classification_ceiling固定为internal，不能称为已完成可配置的人员密级／涉密访问管理。代码枚举里有任务交付／验收等action不等于对应API和完整职责分离已经实现。[当前loader](../../app/authz/loader.py)、[属性条件](../../app/authz/attributes.py)

尚需冻结并逐步落地的管理规则包括：

1. 每条管理action的目标对象、可管理scope与可授予权限上限，是否允许管理自己的任职。
2. 角色revision发布后如何让人员采用新版本，授予／撤销／过期／复职的状态机；不原位改写已发布角色内容。
3. 组织部门／职务与授权scope的关系，数据列表／详情／写接口如何一致过滤；范围不能由前端菜单决定。
4. 权限影响预览与安全的拒绝解释；普通用户错误不泄漏他人身份／资源存在，管理员解释也需要读取权限。
5. 当前实际业务需要时再增加金额门槛、独立reviewer、双人规则和意图批准；不能把登录MFA当批准，不能将两个账号直接等同两个自然人。

管理侧首次实施应走专门的受保护管理协调路径：先按变更前状态验证管理者，再按写者协议修改目标、推进版本和原子审计。不能将改变授权事实的操作塞进当前禁止修改安全事实的普通work handler。

## 7. 安全运营与生产接入的缺口

认证事件、业务审计和控制操作journal已经持久化并限制秘密披露，但尚无管理侧分页检索／导出、可见范围、异常处理和长期清理闭环。[native事件表](../../app/models/native_auth.py#L194)、[本机inspect](../../scripts/native_auth_admin.py#L156)

首轮应定义谁能查什么、如何关联一次管理操作、必要的原因码和保留期限；恢复／重置／停用应有人员通知或可追踪人工交付记录。不是要求收集所有IP／设备信息，更不能把密码、token、OTP或恢复码写入普通审计。清理不得破坏仍需保留的refresh重用检测记录。

当前密码规则为12～256字符与基本字符检查，没有常见／泄露密码阻断。建议补简单本地阻断策略；不默认要求周期性强制改密、复杂字符组合或庞大密码历史。当前会话有绝对期限和敏感操作新鲜度，闲置超时尚未建模，需按管理员／共享终端真实使用场景选择，不把它单列为已证实漏洞。

密钥文件、HTTPS/issuer主机隔离、签名ring换代与备份注意事项已有基础；生产还需验证TOTP加密主密钥换代／重加密、旧备份恢复后的会话与一次性秘密失效、应急人员身份恢复、可信代理和企业共享出口限流。部署文档已说明的限制不能被脚本验收覆盖。[原生运行手册](../../deployment/identity/native-authentication.md)

Maestro实际系统浏览器登录、任职选择、系统安全凭据存储、并发刷新与恢复交互仍单独验收；Stage本机Chromium脚本通过不等于实际桌面客户端已完成。

## 8. 建议的近期交付边界

先补一条真实管理员管理闭环，建议按以下顺序冻结设计与实施，不一次建设完整IAM：

1. 生产初始化／首管交接、管理action与授予范围、近期MFA和应急恢复规则。
2. 管理员创建或邀请一名员工；人员完成单次激活、设置密码、绑定TOTP。
3. 管理员授予一项有限任职；本人发现并选定任职；管理者自提权与越范围授予被拒绝。
4. 安全重置与离职冻结；旧登录／Stage业务资格按约定失效；重复操作、未知结果和并发撤权可恢复。
5. 有权管理员从审计入口看到完整责任链；Maestro完成对应真实交互。

该闭环补足P1b产品缺口；P1c接口设计可并行。P1d持久执行状态、P2任务容量、P3正式流程仍按原阶段推进，不借“企业级”追加独立Agent、多租户、目录同步或通用授权DSL。

Passkey、AD/LDAP/SCIM、身份联邦、公开动态注册、多方恢复、风险引擎等按明确客户需求另评估。它们的缺失不意味着当前分层错误，也不能替代上述最小管理流程。

## 9. 本轮文档校正与证据

核查发现两份现行规格仍有旧表述：私有化API文档把凭据仅归外部IdP；身份schema文档仍称Stage不新建密码/OTP表。这与已交付的原生认证不一致。本轮只修正这些现状描述，并更新OAuth管理手册中组织锁的旧串行说法；历史验收数字及历史决策文档保留原范围。

本次机器清单保存实际25个HTTP操作、相关源码摘要、管理环境限制和最近验证输入一致性，见[评估证据](enterprise-identity-completeness-evidence-2026-10-26.json)。矩阵区分当前事实、目标与本轮建议；不以文档更新宣布管理员产品已经实现。
